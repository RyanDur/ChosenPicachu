# ChosenPicachu

A React and TypeScript site whose home page states its own principles in three concerns: what things are, how they show, how they respond. The code is meant to hold those words up. Every agent working here reads this file first; the pipeline's reviewers are listed at the end.

## Setup

- `npm ci` installs, and its postinstall applies the platform patches in `patches/`.
- `git config core.hooksPath scripts/git-hooks` turns on the hooks that guard every commit and push.
- `npm run dev` serves the site. Feedback appears only with `VITE_APP_FEEDBACK_TOKEN` in `.env`: any value shows it, and a real fine-grained token sends. Never commit a real token.
- `npm run build` typechecks, builds `build/client` with `react-router build`, pre-renders every fixed path into it, and runs `scripts/site-for-pages.mjs`, which lifts the pages out of the `ChosenPicachu` folder into `build/client` and copies the shell to `404.html`; no shell copies are written, since every fixed path is pre-rendered.

## Testing

- Unit and component specs: `npx vitest run`. Journeys: `npx playwright test`, against the stub stage, `scripts/lighthouse/server.mjs` on port 4517, which Playwright starts or reuses.
- The hooks run the gates. Pre-commit runs `oxlint`, `stylelint`, `eslint`, `tsc -b` and vitest; pre-push builds and walks every journey. Run any check by hand when you need it; the hooks make sure it runs.
- Tests pin behaviour, what a reader does or meets, not looks or CSS values. A journey never asserts where something sits, how big it is, what it overlaps, what stays in view, which element scrolls, or how it moves; those are looks, checked by screenshot before a commit. The exception is a look the page itself says in words, such as the list the z-index trap says opened over everything around it: the sentence is what the reader meets, and a journey may measure the page to pin it. A look a card promises is the designer's measurement, not a journey. A sentence a card promises has a test. Why: a test of a style value pins the sheet, not the page. It breaks when the sheet is reworded and passes when the page is wrong ([Dodds on testing what users see](https://kentcdodds.com/blog/common-mistakes-with-react-testing-library), [Fowler's user journey tests](https://martinfowler.com/bliki/UserJourneyTest.html)). Two texts are the canon for every test here, by Ryan's word of 2026-10-25: [Beck's desirable unit tests](https://newsletter.kentbeck.com/p/desirable-unit-tests), so a unit test is isolated, specific and fast, and one that needs a longer wait is asking where it belongs, not for the wait; and [North's Introducing BDD](https://dannorth.net/blog/introducing-bdd/), so a test's name is a sentence about behaviour, written as the reader would meet it, and a scenario has a given, a when and a then. With them, [Playwright's best practices](https://playwright.dev/docs/best-practices) for the journeys and Dodds's list above for the specs; and by the same word, whatever in these four can be a lint rule is a lint rule, so the gate holds it rather than a reader. A spec asserts text only where the text is the behavior: a name a reader uses, an announcement, a count or report computed from data. A paragraph's wording is the reviewer's to read, never the spec's; a spec that pins one is reduced whenever a card touches it, as part of that card (Ryan, 2026-11-01). A parameterized test (test.each) exists only to guard against drift, the same behavior across browsers, operating systems or the site's own builds of one feature, or every page in the site's page list; everything else is one named test per case, never a loop over a list, whether the rows expect the same thing or not (Ryan, 2026-11-01). One exception: a sequence a reader performs in turn on one page (trying each choice, then the next) may be one test whose answer is the list of steps that went wrong, each named with what failed.
- Every journey fails if the page throws an error it did not ask for, after any click or drag, not only on arrival: journeys take `test` from `e2e/__test_support/journey.ts`, never straight from `@playwright/test`. Why: a page error after an interaction reaches no assertion, and Lighthouse only ever saw the page as it loaded, in Chrome (Ryan, 2026-11-07).
- Lighthouse gates bytes, not a score. Each audited page has a budget in `lighthouserc.json` for its document, its style sheets and its script, set from what it loaded on 7cf6d958 plus about 5%, and a catch-all ceiling holds any page without one. A change that goes over raises that page's budget in the same commit and says why, and a new audited page gets its own budget with the card that adds it. Accessibility still gates at 1. Performance, best practices and SEO are reported in the run's summary but gate nothing. Why: the performance score is a simulated slow phone that moved by up to 0.2 between runs of the same build and failed pushes on noise, while a page's bytes are the same every run. Our own checks cover the rest: errors in the journeys, titles and descriptions in `e2e/names.e2e.ts`, markup in html-validate (Ryan, 2026-11-07).
- Tests find what a reader finds: by role, label and text, never by class. Page objects live in the owner's `__test_support`.
- Journeys run as a reader who asks for less motion, and none is retried or skipped. Animation and transition are style, so no test measures them: not a fold's heights as it slides, not a banner's frames, not a pill's paint. Motion is looked at before a commit, like any other look, and it fails gracefully where an engine can't do it. Why: Ryan, 2026-10-05, "We do not test style. The animation and transition is a style concern, so we don't test that. I know interpolate size doesn't work in those browsers. The style should fail gracefully." And: "we should not have to skip any tests if we are just testing behavior." A journey that reads frames passes or fails with the runner's load: in eight pipeline runs, 13 journeys passed only on a retry, most of them motion. Four journeys still run in one engine only, because the test tooling cannot stage them in the others, not because the behaviour differs: a finger dragging a table's column (Playwright moves a finger only through Chromium's DevTools protocol, and a pointer dispatched from the page fails `setPointerCapture` in every engine), a users page reloaded past its worker (a reload that bypasses the worker exists only in Chromium's DevTools protocol), and a worker script that never answers (only WebKit lets a route hold it). They wait on Ryan's ruling. A fifth runs in Chromium only by Ryan's ruling: a finger cancelled mid-resize (`e2e/resize-reports.e2e.ts`; only Chromium's DevTools protocol cancels a finger; Ryan, 2026-10-22, allowed and recorded here). A sixth runs in Chromium only by Ryan's ruling: a finger cancelled on a chart's grip (`e2e/charts.e2e.ts`; only Chromium's DevTools protocol cancels a finger; Ryan, 2026-10-25, allowed and recorded here). A seventh runs in Chromium only by Ryan's ruling: a finger cancelled on a sortable list's grip (`e2e/drag-sort.e2e.ts`; only Chromium's DevTools protocol cancels a finger; Ryan, 2026-11-01, allowed and recorded here, and the same day he ruled that a Chromium-only journey an all-engine one covers is deleted). No other skip joins them. One journey is run once for a different reason: the crawler's reading of each static page's title and description (`e2e/names.e2e.ts`) fetches served HTML through the request fixture and opens no browser, so a second engine would check nothing new; it runs under the Chromium project alone (designer, 2026-10-08).
- A test that passes only on retry or alone is a defect. Before blaming a test, check the machine: `pmset -g adapter` should show the full charger, and a killed Playwright run can leave its stage server on 4517 for later runs to reuse.
- While someone else verifies from this checkout, leave its `build/client` alone: `react-router build` takes no `--outDir`, so build in a scratch worktree instead.
- A build runs with the same values as the `env.js` it is served with, so a push worktree needs the `.env`. Why: a pre-rendered page carries env-dependent markup, the Feedback slot and the chart's product, and React does not patch markup that differs on hydration; it throws the page away (React #418). Production emits `env.js` from the build's own values and CI sets the same values for the build and its stage; `hydration.e2e` loads every pre-rendered page and fails on a drift.

## The site's look

Each rule gives its reason, and a source where one exists outside this repo. A rule whose reason no longer holds is a question for Ryan, not a rule to drop.

- The site teaches by example. The frame is neutral and plain; the exhibits are polished. The home page is Ryan's philosophy of writing frontend code; the demos grow in complexity, accordions first. Why: a reader comes for the exhibits, and a plain frame keeps their eye there. The order lets each demo lean on the one before.
- A tutorial is written for a working developer who has hit the bug its tab is about, often a seasoned one from other work (back end, native, data) who hasn't learned how CSS and the browser work underneath, with newcomers kept in mind. Every term is defined where it first appears, basics included. Headings and captions carry the answer. Every idea has an example to press, and a drawing where it helps. A tab opens with the problem and its point of view, never with how to build. Accordions start with HTML alone, and on the simple tabs depth sits in a fold below the point. Why: a reader who lands from a search with a bug in hand needs the answer before the build, and the less a learner has to attend to, the more room they have to understand. The review holds tutorials to this through `scripts/review/tutorials.md`.
- Anything the frame owns (rail, header, footer, dialogs, controls) is dressed from the frame's own words: `backdrop` ground, `field` bars parted by the `--base` gap, `bare card` inputs under a bold `field` label bar, `path attentive field reachable` for a bar with a word, `icon-button borderless field attentive reachable` for an icon, `hairline-outline` for a secondary, `alarm-ink` for a refusal. The gap is the only empty space a reader sees; parts fill their cells edge to edge. The frame never wears `card`, `rounded-corners`, `lifted`, bordered inputs or filled buttons; those belong to the exhibits. Why: when the frame borrows an exhibit's dress, a reader can no longer tell the site from what it shows. One vocabulary means a new control is dressed by naming its needs, not by writing new rules.
- A primary button is the site's inverted bar, `--field-inverse` with the `--field` word, and every state is drawn: approach on hover and focus, the `--ring` on focus-visible, `--press-glow` on active, `--smoke` or `--ink-muted` when disabled, with no hover. Why: a state that isn't drawn is a state the reader can't see. Keyboard users need to see focus ([WCAG 2.4.7, focus visible](https://www.w3.org/WAI/WCAG21/Understanding/focus-visible.html)), and a disabled button that still lights on hover invites a press that does nothing.
- Markup is form and HTML5 elements only: `dialog`, `form`, `fieldset` with an off-screen `legend`, `label`, `textarea`, `input`, `output`, `button`, `hgroup`, `section` with a heading. A `footer` inside a dialog is a second landmark; an unnamed `section` owes a heading; a group of controls is a `fieldset`. Why: the element is the meaning a screen reader announces, and a `div` means nothing ([HTML, the div element](https://html.spec.whatwg.org/multipage/grouping-content.html#the-div-element)). A native element brings its role, states and keys with it, so ARIA comes last ([the first rule of ARIA](https://www.w3.org/TR/using-aria/)). A group of controls needs its legend to be named ([WCAG technique H71](https://www.w3.org/WAI/WCAG21/Techniques/html/H71)).
- Prose reaches across the container it sits in. No width cap, a measure or any other, stops a paragraph partway across its part of the page. Where words sit beside code or a drawing, that column is their container and they fill it. Why: Ryan, 2026-10-04, "I do not want the text to just suddenly stop in a random part of the page", after the tab introductions were capped at 75 characters and sat beside an empty half of the page. He had said the same on 2026-09-26. A cap for line length leaves a hole that reads as unfinished, and the site's lines are his to set.
- Forms keep their niceties: Enter submits, Shift+Enter makes a new line in a textarea, an empty field is refused in the platform's own words, the phone keyboard's key reads "send", and the contact field offers the reader's email. Why: these are what a reader's hands already expect from every other form. The platform's refusal is worded and translated by the browser and read by assistive tech. The keyboard's key comes from [enterkeyhint](https://developer.mozilla.org/en-US/docs/Web/HTML/Global_attributes/enterkeyhint). Errors follow the established patterns rather than invented ones ([GOV.UK validation](https://design-system.service.gov.uk/patterns/validation/), [Nielsen Norman Group on form errors](https://www.nngroup.com/articles/errors-forms-design-guidelines/)).
- A modal fits the view and never scrolls. On a phone it fills the view, laid out for upright and sideways, and the field is the part that grows. The reset leaves the browser's dialog positioning and backdrop alone and zeroes only its padding and border. Why: a modal that scrolls hides its own buttons, and on a phone the keyboard takes half the view already. The browser's [dialog](https://developer.mozilla.org/en-US/docs/Web/HTML/Element/dialog) already centres itself, dims the page and traps focus, so the reset takes away only what the design replaces.
- Text flows: explanatory prose has no line-length clamp, and each run takes the room its row gives it, as the recipe steps do. Look at the other demos before writing a layout rule. Why: Ryan's ruling, so every demo reads the same way.
- Touch targets are 44px, gated on `pointer: coarse`, never on width. Check both orientations. Why: 44px is the size a finger can hit ([WCAG 2.5.5, target size](https://www.w3.org/WAI/WCAG21/Understanding/target-size.html)). Width says nothing about the pointer: a narrow window on a desktop has a mouse, and a wide tablet has a finger. The [pointer media feature](https://developer.mozilla.org/en-US/docs/Web/CSS/@media/pointer) asks the right question.
- The site's bold is 600 everywhere, through the `bold` modifier in `src/styles/typography.css`, and the frame's sheets declare no font. Why: one weight in one place. A sheet that writes its own weight or size drifts from the rest, and a change to the type scale has to reach every word.
- The platform first: `details` and `popover` before script, and script as the enhancement, so a failure leaves a working page (a button with an invoker command keeps a click fallback). Why: what the browser does can't break when the script doesn't load, and it comes with keys and announcements already ([details](https://developer.mozilla.org/en-US/docs/Web/HTML/Element/details), [the Popover API](https://developer.mozilla.org/en-US/docs/Web/API/Popover_API), [progressive enhancement](https://developer.mozilla.org/en-US/docs/Glossary/Progressive_Enhancement)). Browsers without [invoker commands](https://developer.mozilla.org/en-US/docs/Web/API/Invoker_Commands_API) still need the button to work.
- Every fold moves by transition, never animation. Reduced motion is honoured once, in the reset, and then every fold opens at once. Why: a [transition](https://developer.mozilla.org/en-US/docs/Web/CSS/CSS_transitions) turns around from wherever it is when the reader presses again midway; an animation plays out on its own clock. CSS owns all motion, so script only sets state. A reader who asks for [less motion](https://developer.mozilla.org/en-US/docs/Web/CSS/@media/prefers-reduced-motion) gets none, from one block, and no component can forget it ([WCAG 2.3.3, animation from interactions](https://www.w3.org/WAI/WCAG21/Understanding/animation-from-interactions.html)).
- Every gesture has a keyboard twin, in the order the eye reads: one order for the eye and the screen reader. Why: a drag with no keys shuts out anyone without a mouse ([WCAG 2.1.1, keyboard](https://www.w3.org/WAI/WCAG21/Understanding/keyboard.html)), and focus that jumps against the reading order loses the reader ([WCAG 2.4.3, focus order](https://www.w3.org/WAI/WCAG21/Understanding/focus-order.html), [1.3.2, meaningful sequence](https://www.w3.org/WAI/WCAG21/Understanding/meaningful-sequence.html)).
- Diagrams grow to their desktop size and no further, sit centred in a wider column, shrink to a phone's column with their words held at caption size, and draw with non-scaling hairlines. Why: stretched to their column, a label read 27px on an upright iPad and 11px on a phone (#29). Capped at the drawing's own 320px, they read too small on a desktop, so Ryan set the cap at the desktop size. Lines stay hairlines through [vector-effect](https://developer.mozilla.org/en-US/docs/Web/SVG/Attribute/vector-effect).

## Code style

- The reviewers' rubrics below are the style: the three concerns on the home page, `scripts/review/design.md`, `scripts/review/tests.md`, `scripts/review/voice.md` for how the site's prose reads, and `scripts/review/plain.md` for the review's own words.
- The semantic element first; a `div` is the last resort. Native elements before ARIA roles.
- No `document` or `window` in React code, and a ref only for one of two reasons. A component that needs its element uses the platform's declarative attribute for it first: `commandfor` and `command`, `popover`, `autofocus`, a fragment link and `:target`. A `useRef` is allowed only (1) to hold a `dialog` the component shows as a modal with `showModal()`, or (2) to read the element's own details, such as its measured size, when nothing else gives them, such as an event. A behavior that fits neither is dropped. It is never rebuilt with a ref or a lookup by id. `createRef` and `forwardRef` are never used. A value kept between renders is state. ESLint refuses `useRef`, `createRef` and `forwardRef` outside the files listed in `refsWithAReason` in `eslint.config.mjs`. A file joins that list in the commit that adds its ref, and the commit says which of the two reasons it is. Why: Ryan's ruling on refs, relayed by the dev on 2026-10-05; "Platform attributes only" on 2026-11-07, when the ban on `document` met it; and the same day: "there are two expceptions for why a ref is used. one is for a dialog when we need to show a modal. second is if you need the elements details and you have nowhere else to get them from like an event".
- CSS: structure in the component's own sheet, shared needs from `src/styles`, and type only from `src/styles/typography.css` classes on the element. A tag is styled only in the reset; everywhere else a rule names a class, so a table's cells and a fold's parts wear a word. Why: the home page's Presentation concern says "Element selectors are used only in the reset". A rule on a bare tag reaches every such element a later change puts inside the component, and the class list no longer says what the element is. Two gates hold the sheets and the class lists to this: stylelint refuses a look (colour, border, type, shadow, radius, fill) in a component sheet, with no excused list, since geometry, counters, opacity and overflow are structure; and ESLint refuses a class no sheet's selector reads and an own class put behind a shared word. An element no sheet styles wears no noun: its tag and its text say what it is, and a class nobody reads says nothing. Why: Ryan, 2026-10-09, "No noun". A component's specific sheet stays near the component and the shared styles at the root. Why: Ryan, 2026-10-09, "in a react app, keep the specific style sheet near the component, and all the shared styles at the root". For the class gate, near means the component's own directory or any directory above it, so a family's shared sheet sits at the family's root, and the shared words in `src/styles` always count. Why: Ryan, 2026-10-09, "Own dir or ancestor", picked from the dev's census (283 classes in 39 files written outside that reach). The table family follows a second ruling of his the same day, "Parts dress themselves": DragSortableTable's parts write their own structural classes and a page passes only its column words; the vanilla table frame is its own world and counts the sheets it imports.
- A comment says why, and only when the cause is outside our control: a browser's behaviour, a platform rule, a library's shape, a tool's directive. A comment that says what the code does, or why we chose it, is a sign to refactor or to leave out. Why: Ryan, 2026-10-05, "If code needs a comment to explain what it does, refactor. Comments are for why when the cause is outside our control." The sweep that applied it (about 80 lines in 38 files) kept the comments on WebKit's paint and Tab, Firefox's sixtieths of a pixel, `var()` in `@media`, Coinbase's maker side and the like, and dropped the rest.
- No default exports. ESLint's `no-restricted-exports` refuses them, so every module is imported by the name of its one function. The rule exempts only the files whose default the framework or a tool requires: `src/root.tsx`, `src/routes.ts`, the seventeen route modules named in `routeModules` in `eslint.config.mjs`, the tools' `*.config` files and type declarations. Why: Ryan, 2026-11-07, "NO DEFAULT EXPORTS. this should be a linting rule." The route list is written out, not read from `src/routes.ts`, so a new route file cannot earn a default by being listed there. A new page is a parameter on a route that exists, or a change to that list that a reviewer sees. Why: on 2026-11-07, three route files were written for #325 with defaults, and #325 shipped as one parametered route instead.
- React code never reaches for `document` or `window`. ESLint's `no-restricted-globals` refuses both in `src`. The plain-script builds are exempt, and they live in their own directories (`vanilla` in `eslint.config.mjs`). If plain-script code sits anywhere else, it moves into its build's directory. The framework's two boot files, `src/entry.client.tsx` and `src/env.ts`, are exempt too. The files that still reach for the page are listed in `stillReachForThePage`. A file comes off that list when a commit touches it, and nothing is added. Why: Ryan, 2026-11-07, "react should never need anything to use document" and "if it is in vanlla, then it needs to move to vanilla".
- Motion is the style sheet's alone. Script never starts a transition or an animation: `no-restricted-properties` refuses `startViewTransition` and `animate` in `src`, and `stillMoveByScript` lists the one file that still does (`src/components/glide.ts`). Script may set a state class or attribute that a style sheet animates, and it may read that an animation ended. Why: Ryan, 2026-11-07, "react should not be in charge of any transitions or animations, nor should javascript" and "they should solely be css's domain".
- Motion moves only what the GPU composites: `transform`, `translate`, `rotate`, `scale`, `opacity` and `filter`. A transition or a keyframe on anything else, `all` included, makes the browser lay out or paint every frame, and stylelint's `chosen/compositor-motion` (scripts/lint/motion.mjs) refuses it. The discrete flips that let an element animate out (`visibility`, `content-visibility`, `display`, `overlay`) are allowed, since they change once and do not move. One layout motion is allowed: a grid track, `grid-template-rows` or `grid-template-columns`, opening from 0fr to 1fr or closing back. A fold's text and a gap in the banner stack open that way, sized by their content with nothing measured. The sheets that still animate other properties are listed in `stillMoveOnTheMainThread` in `stylelint.config.js`. A sheet comes off the list when a commit touches it, and nothing is added. The demos have no exception: the Accordions tab's folds and the Charts tab's bars and points move by these properties too, so a lesson about a layout-moving trick shows that trick in its samples, never running. Why: Ryan, 2026-11-07, "motion should also be restricted to the properties that take advantage of the gpu", and "No exceptions" when asked whether the Accordions and Charts exhibits were exempt. The grid track came later the same day: "you could put the row animation on the ::details-content", then "any 0fr↔1fr track".
- A component takes what an element takes: attributes, such as a name, a label or an id, its children, and the handlers an element would fire. State is owned by a context, never passed from component to component. A component that needs state reads it from its context's hook, and a component that changes state dispatches to that context. No prop carries state down or a setter up. State that changes together is one reducer: its parts are one state type, its changes are named actions, and its transitions are a reducer passed to `useReducer`, as `DragSortableTable` does. The context's provider holds that reducer. Three or more `useState` calls in a file are a sign of a missing reducer. Values the address holds are read through the context's own hook over the address (`useControls` for the demo dials, `useGallery` for the gallery), never copied into state. Existing files take this shape when a commit touches them. Why: Ryan, 2026-11-07, "if there are many useStates in a file, that is a good chance to use useReducer and maybe a react context", then "I don't think we should ever need to pass state from component to component. I think you geve a component what you would give an element. and state is owned by context".
- Every directory of code has an index, and the index is where its exports leave the directory. Code outside a directory imports the directory, never a file inside it. An index exports only what code outside imports, named, from the files directly in it: a subdirectory exports through its own index, and an importer reaches that subdirectory directly. A `.ts` file exports one module, and a `.tsx` file one component, with their types. A module is an object whose name is its namespace, `export const carve: Carve = {unit, span, withoutImports};`. It is a function only when it needs something to be built from, such as `recentTrades(base, product)`, or when it holds state of its own, such as a store, so that each caller and each test gets a fresh one. Its behaviors are always called as methods on that name, `carve.unit(...)`, never destructured or imported loose. Why: Ryan, 2026-11-07, "it onlu needs to be a function if it needs something … else it is just an object and the name serves as a form of namespace" and "then the function is always a method call on the variable". Four ESLint rules in `scripts/lint/structure.mjs` hold this: `one-export`, `has-index`, `through-index` and `index-top-level`. Tests, test support and the framework's route modules are exempt. The files that broke a rule on 2026-11-07 are listed in `scripts/lint/structure-exceptions.json`. A listed file that now keeps its rule fails the lint until it comes off the list, so the lists only shrink, and nothing is added. A commit that moves a listed file moves its entry. Why: Ryan, 2026-11-07, "an index for every directory", "tha is where exports ouside of the directory happen", "but it only exports the top level", "sub-directories export what they export, butt importers need to reach that directory", and "go with the shrinking exception list".
- Every list of files that still break a rule ends empty, and the debt pass is not over until it does: `scripts/lint/structure-exceptions.json`, `stillReachForThePage`, `stillMoveByScript` and `stillMoveOnTheMainThread`. When a list is empty, the commit that empties it deletes the list and its exemption code. `routeModules` and `refsWithAReason` are not debt: the first is what the framework requires, the second names the two reasons a ref is allowed. Why: Ryan, 2026-11-07, "keep the ratchet, but all must be gone by the end".
- `npm run format` formats with ESLint Stylistic. Lines hold to 120 columns (`max-len`). Strings, template literals, regular expressions and URLs are exempt, so test titles stay whole and searchable. No rule enforces the JSX shape, so it is written here: the first props sit on the tag's line and the rest wrap below it, `>` and the closing tag follow the content, and `return <>` takes no parens. Prose in JSX breaks only between two words in one text run, never beside an element or a `{' '}`, so what renders does not change. Why: Ryan asked for Stylistic in place of WebStorm's reformat on save (2026-11-02). The designer set 120 because it is WebStorm's right margin, the width his saves already kept, and kept the JSX shape the code already had, since he asked for a new tool, not a new look (designer, 2026-11-02).
- Every route module draws its whole page, frame and content, at build time, and no route is lazy. Why: framework mode splits each route module into its own chunk itself, and the pre-render needs the page in the document; a page left lazy inside its module pre-rendered as an empty block that script revealed, which Lighthouse read as a layout shift of 0.226 and a reader without script read as an empty page (#243, 2026-10-25). The earlier rule that a lazy route's `handle` is given in an eager routes module is retired with the lazies; its reason, that a frame arriving late moves under the reader's finger ([#126](https://github.com/RyanDur/ChosenPicachu/issues/126), 3fb2e9c0), still holds and is now met by the document itself.
- TypeScript is written as modules, never classes. A module is one function that returns an object of behaviors, each one a transformation of data, and a `.ts` file exports that one function and nothing else: no free-floating exported functions beside it, whatever TypeScript's own file modules allow. A React component in a `.tsx` file is its own shape and is not held to this. Those functions are what a result object takes: a step passes them to sand's `Result` or `Maybe`, through `map`, `mBind` or `either`, so the data moves through the result one transformation at a time. sand has three: `Result`, `Maybe` and `asyncResult`. No bare promise appears in `src`: no `await`, no `.then`, no `new Promise`, and no function that returns a `Promise`. A promise the platform hands over, such as a fetch, a service worker's registration or a dynamic import, is wrapped in `asyncResult` where it arrives, and its data moves through `asyncResult`'s functions from there. Tests and journeys may await, since their runners are built on promises. One module serves one domain, in Fowler's sense of a [bounded context](https://martinfowler.com/bliki/BoundedContext.html), and a domain may hold subdomains; `docs/contexts.md` maps the site's contexts and where each file belongs, so a loose function goes inside the module of its context, as one of its behaviors. A module may export its types beside its function. A file whose shape the framework fixes keeps it: `routes.ts`, `react-router.config.ts` and a route module's exports. Page objects are test code, so they may await, and they take the module shape when touched. The [SOLID](https://en.wikipedia.org/wiki/SOLID) principles hold for the modules: each has one reason to change, and a caller depends on the object it is handed, not on how that object was built. Where the platform or a library already does a job, the code uses it, and a hand-written stand-in for it is a hack to remove. Existing files take this shape when a commit touches them, never in a sweep. Why: Ryan, 2026-11-07: "I don't like classes but I do like functions that return objects that transform data that cna be passed into a result object", then "the moules functions can be passed to a reult objects funtions to transform the data", and "we have result maybe and asyncReslt. I shouldn't see any bare promises", and of `src/components/scroll.ts`, "I want to get rid of hacks like this", and "I do not want free floating functions. I know that ts exports as a module. I want one function that retunrs an object of behaviors".

## Commits and pushes

- The dev writes and tests code. The designer may change documents and CI directly: this file, the review's rubrics and prompts in `scripts/review/*.md`, and the workflows. Why: Ryan, 2026-10-03, "the dev is in charge of writing and testing code, you can update documents and ci".
- Only reader value becomes a story on the board; tooling is done directly. The designer drafts cards, and a card is promoted when agreed. A Done card is never reopened: a change of direction is a new card. Why: the board is the product's backlog, and the designer verifies each card against what a reader meets. Tooling has no reader to verify for. A reopened card rewrites what was already shipped and checked.
- The dev works on local main so Ryan can watch, uses a worktree only to push a slice ahead, and says "ready" with a clean tree. The designer verifies on main, from the checkout's `build/client`, and holds it until the verdict. Nobody runs journeys while a push is in flight. Why: Ryan sees work only once it's on local main. A verifier who builds from a tree with someone else's uncommitted work measures something that will never be pushed. The journeys share one stage port, so two runs at once test each other's build.
- Before the ready, the dev pushes the card's commits to a branch named `verify/<issue>` (`verify/debt-<area>` for a debt slice, which has no card) rather than running the journeys locally, so neither dev waits for the machine or for the other's run. The dev commits the card on a local branch of the same name. The pre-commit hook runs only the linters on a `verify/` branch, which take seconds and catch formatting while the file is open, and the pre-push hook runs nothing for a push that only goes to `verify/` branches. After Accepted, the dev rebases the branch onto main and fast-forwards main to it, and main's hooks run in full on that push. That push runs the unit tests, the journeys and the review, and nothing else: Lighthouse, the deploy and the smoke run only from main. The ready names the branch run. Main is unchanged: it still waits for Accepted and runs everything, the review included. The designer deletes the branch once its commits are on main.
- A push carries at least seven commits. After the seventh, the dev keeps working until the context in hand is finished, and pushes there, never in the middle of one. This holds for the designer's docs too. Why: Ryan, 2026-11-07, "I want at least seven commits or nearest context grouping after that".
- One push carries a whole slice: its code, its words, and its answers to the last review. A review's concerns and notes, on a verify branch or on main, are answered in the dev's next push, usually the next slice. They never get a push of their own, and a run's review is never answered by another run. A words-only or one-line fix never gets its own branch: it rides in the nearest push. No one waits for CI: the dev pushes on the designer's Accepted, then starts the next slice at once, and a red job or a review's finding, a violation included, is fixed in the dev's next push with the new code. A red job on main stops the deploy for both devs, so its fix comes first in that push. Why: Ryan, 2026-11-07, "I think we can group more of the debt, we are running ci on text changes, when we have so much to get through", and "that would also mean that we don't have to wait for ci, we can just keep moving, and put any fixes into the next push with the new code". Why: Ryan, 2026-11-07, "we wouldn't always need to wait for the resources to be available if you could push to a branch to run the tests", and that it "can also get feedback"; "main is the big one", and "this way, neither dev needs to wait for the other to be finished", and "we don't need the precommit hook on pushes to branches".
- One commit per fix. A card's batch goes out in one push, after the designer accepts it. Review findings, violations included, are answered in one batch per card. Why: every push costs a full pipeline and a review, and a batch lets the review read the answers together.
- A card is Done when it is in production, every pipeline job is green including the review, and every review finding is fixed or argued in a commit message until the reviewer agrees. Why: the pipeline's reviewer reads the git log, not the board. A finding answered only in a comment is never seen by the one who raised it.
- A commit quotes the review finding it answers, and a decline gives its reason in the commit: the pipeline's reviewer reads the log.
- A reducer's actions are made by action creators: `dispatch(answered(answer))`, never `dispatch({type: 'answered', answer})`. The creators live beside the reducer, as Feedback's and UserInformation's do. ESLint refuses an object written inside `dispatch(...)`. Why: Ryan, 2026-11-07, "if we are doing a redux style we can create an action creator".
- A component that takes children types them with `PropsWithChildren<Props>`, never with `children` as a key of its props type. ESLint refuses a `children` key in any type. Why: Ryan, 2026-11-07, "we should never have to put children in a props list", "use PropsWithChildren".
- A change that shortens a line rejoins the wrap it no longer needs. ESLint's `wrap/needless-wrap` (scripts/lint/wrap.mjs) refuses a value left on its own line after `=` when it would fit on the line above within 120 characters, and `eslint --fix` joins it. Why: Ryan, 2026-11-07, on a `useControls()` call left on the line below its name: the devs were not fixing the formatting when they updated code.
- Linear history: no merge commits. A dev may force-push its own `verify/` branch after a rebase, with `--force-with-lease` (Ryan, 2026-11-07: "yes, let them force-push verify branches"); main is never force-pushed. A dev pushes a new `verify/` branch with `-u` (`git push -u origin HEAD:verify/<name>`), so the local branch tracks it: when the designer deletes the remote after the code is on main, `git gone` removes the local one. Why: Ryan, 2026-11-07, "we should clean up branches, when the code is on main". A branch reaches main by rebase and a fast-forward push, never by a merge or a pull request merge. GitHub refuses anything else on main: it requires linear history, for admins too, and allows no force push. Why: Ryan, 2026-11-07, "we must keep a linear hsitory, rebase only".

## The review

A lead reads the rubric, sends each reviewer the scope, corroborates every finding that comes back, and answers in the feedback stance: habits first, then plusses and deltas. Every reviewer holds the values in `scripts/review/values.md` and writes by `scripts/review/plain.md`.

`scripts/review/prompt.mjs` builds the lead's prompt and `scripts/review/agents.mjs` builds the reviewers, both from the list under Reviewers below. A reviewer added there joins the next review; one removed there leaves it.

### Run it before a push

The pipeline's own command, from the repo's root, on the commits about to be pushed:

```sh
export REVIEW_SCOPE=changes REVIEW_BEFORE=$(git rev-parse origin/main) REVIEW_AFTER=$(git rev-parse HEAD)
claude --print "$(node scripts/review/prompt.mjs)" \
  --output-format stream-json --verbose \
  --json-schema "$(cat scripts/review/feedback.schema.json)" \
  --agents "$(node scripts/review/agents.mjs)" \
  --allowedTools "Agent,Read,Grep,Glob,Bash(git diff:*),Bash(git log:*)" \
  --max-turns 80 \
  --no-session-persistence | node scripts/review/narrate.mjs
node scripts/review/report.mjs < review.json
```

The pipeline runs the same through `npx --yes @anthropic-ai/claude-code@2.1.281` with its own model. The other scopes are `full`, the whole of `src/` and `e2e/`; `tests`, every test; and `design`, the whole site.
