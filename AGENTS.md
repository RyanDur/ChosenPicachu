# ChosenPicachu

A React and TypeScript site whose home page states its own principles in three concerns: what things are, how they show, how they respond. The code is meant to hold those words up. Every agent working here reads this file first; the pipeline's reviewers are listed at the end.

## Setup

- `npm ci` installs, and its postinstall applies the platform patches in `patches/`.
- `git config core.hooksPath scripts/git-hooks` turns on the hook that guards every push.
- `npm run dev` serves the site. Feedback appears only with `VITE_APP_FEEDBACK_TOKEN` in `.env`: any value shows it, and a real fine-grained token sends. Never commit a real token.
- The dev server paints each page without its styles until the page's script loads, because in dev Vite delivers the CSS through the scripts. The build links the stylesheet in the head, so the live site has no such flash. Judge looks, layout shift and timing on a build served by `STAGE_PORT=<port> node scripts/lighthouse/server.mjs`, never on `npm run dev`. Why: Ryan, 2026-11-08, chose to leave the dev flash alone rather than add dev-only code that links the styles, since a dev that links many CSS files can order the cascade differently from the build's one file.
- `npm run build` typechecks, builds the client into `build/client` and the server entry into `build/server`, then runs `scripts/prerender.mjs`. The script draws every path in `prerender.pages` into its own `index.html`, with that page's scripts preloaded, and writes the 404 shell to `404.html`.

## Testing

- Unit and component specs: `npx vitest run`. Journeys: `npx playwright test`, against the stub stage, `scripts/lighthouse/server.mjs` on port 4517, which Playwright starts or reuses.
- A commit runs nothing, and the pre-push hook runs only `oxlint`, `stylelint` and `eslint`, which take seconds. Everything else runs in the pull request's checks. Run any check by hand when you need it. Why: Ryan, 2026-11-08, "build_test review lighthose and journeys happen on PR's", so a push no longer repeats what the pull request runs, and "maybe we should remove the precommit and add its checks to the pre-push".
- Tests pin behavior, what a reader does or meets, not looks or CSS values. A journey never asserts where something sits, how big it is, what it overlaps, what stays in view, which element scrolls, or how it moves; those are looks, checked by screenshot before a commit. The exception is a look the page itself says in words, such as the list the z-index trap says opened over everything around it: the sentence is what the reader meets, and a journey may measure the page to pin it. A look a card promises is the designer's measurement, not a journey. A sentence a card promises has a test. Why: a test of a style value pins the sheet, not the page. It breaks when the sheet is reworded and passes when the page is wrong ([Dodds on testing what users see](https://kentcdodds.com/blog/common-mistakes-with-react-testing-library), [Fowler's user journey tests](https://martinfowler.com/bliki/UserJourneyTest.html)). Two texts are the canon for every test here, by Ryan's word of 2026-10-25: [Beck's desirable unit tests](https://newsletter.kentbeck.com/p/desirable-unit-tests), so a unit test is isolated, specific and fast; and [North's Introducing BDD](https://dannorth.net/blog/introducing-bdd/), so a test's name is a sentence about behavior, written as the reader would meet it, and a scenario has a given, a when and a then. With them, [Playwright's best practices](https://playwright.dev/docs/best-practices) for the journeys and Dodds's list above for the specs; and by the same word, whatever in these four can be a lint rule is a lint rule, so the gate holds it rather than a reader. A spec asserts text only where the text is the behavior: a name a reader uses, an announcement, a count or report computed from data. A paragraph's wording is the reviewer's to read, never the spec's; a spec that pins one is reduced whenever a card touches it, as part of that card (Ryan, 2026-11-01). A parameterized test (test.each) exists only to guard against drift, the same behavior across browsers, operating systems or the site's own builds of one feature, or every page in the site's page list; everything else is one named test per case, never a loop over a list, whether the rows expect the same thing or not (Ryan, 2026-11-01). One exception: a sequence a reader performs in turn on one page (trying each choice, then the next) may be one test whose answer is the list of steps that went wrong, each named with what failed.
- A unit spec is quick. When one times out on a page that is correct, the question is what it renders and whether it belongs in a journey, never a longer wait. Why: Ryan, 2026-10-25, "why is it failing? why is it taking too long? is it tested in the right place? the unit tests should be quick".
- Every journey fails if the page throws an error it did not ask for, after any click or drag, not only on arrival: journeys take `test` from `e2e/__test_support/journey.ts`, never straight from `@playwright/test`. Why: a page error after an interaction reaches no assertion, and Lighthouse only ever saw the page as it loaded, in Chrome (Ryan, 2026-11-07).
- Lighthouse gates bytes, not a score. Each audited page has a budget in `lighthouserc.json` for its document, its style sheets and its script, set from what it loaded on 7cf6d958 plus about 5%, and a catch-all ceiling holds any page without one. A change that goes over raises that page's budget in the same commit and says why, and a new audited page gets its own budget with the card that adds it. Accessibility still gates at 1. Performance, best practices and SEO are reported in the run's summary but gate nothing. Why: the performance score is a simulated slow phone that moved by up to 0.2 between runs of the same build and failed pushes on noise, while a page's bytes are the same every run. Our own checks cover the rest: errors in the journeys, titles and descriptions in `e2e/names.e2e.ts`, markup in html-validate (Ryan, 2026-11-07).
- Tests find what a reader finds: by role, label and text, never by class. Page objects live in the owner's `__test_support`.
- Journeys run as a reader who asks for less motion, and none is retried or skipped. Animation and transition are style, so no test measures them: not a fold's heights as it slides, not a banner's frames, not a pill's paint. Motion is looked at before a commit, like any other look, and it fails gracefully where an engine can't do it. Why: Ryan, 2026-10-05, "We do not test style. The animation and transition is a style concern, so we don't test that. I know interpolate size doesn't work in those browsers. The style should fail gracefully." And: "we should not have to skip any tests if we are just testing behavior." A journey that reads frames passes or fails with the runner's load: in eight pipeline runs, 13 journeys passed only on a retry, most of them motion. Four journeys still run in one engine only, because the test tooling cannot stage them in the others, not because the behavior differs: a finger dragging a table's column (Playwright moves a finger only through Chromium's DevTools protocol, and a pointer dispatched from the page fails `setPointerCapture` in every engine), a users page reloaded past its worker (a reload that bypasses the worker exists only in Chromium's DevTools protocol), and a worker script that never answers (only WebKit lets a route hold it). They wait on Ryan's ruling. A fifth runs in Chromium only by Ryan's ruling: a finger canceled mid-resize (`e2e/resize-reports.e2e.ts`; only Chromium's DevTools protocol cancels a finger; Ryan, 2026-10-22, allowed and recorded here). A sixth runs in Chromium only by Ryan's ruling: a finger canceled on a chart's grip (`e2e/charts.e2e.ts`; only Chromium's DevTools protocol cancels a finger; Ryan, 2026-10-25, allowed and recorded here). A seventh runs in Chromium only by Ryan's ruling: a finger canceled on a sortable list's grip (`e2e/drag-sort.e2e.ts`; only Chromium's DevTools protocol cancels a finger; Ryan, 2026-11-01, allowed and recorded here, and the same day he ruled that a Chromium-only journey an all-engine one covers is deleted). An eighth runs in Chromium only by Ryan's ruling: a column whose mouse button is let go outside the page (`e2e/eager-pace.e2e.ts`; only Chromium's DevTools protocol sends a pointer move with no buttons pressed while one is held; Ryan, 2026-11-08, allowed and recorded here). No other skip joins them. One journey is run once for a different reason: the crawler's reading of each static page's title and description (`e2e/names.e2e.ts`) fetches served HTML through the request fixture and opens no browser, so a second engine would check nothing new; it runs under the Chromium project alone (designer, 2026-10-08).
- A test that passes only on retry or alone is a defect. Before blaming a test, check the machine: `pmset -g adapter` should show the full charger, and a killed Playwright run can leave its stage server on 4517 for later runs to reuse.
- While someone else verifies from this checkout, leave its `build/client` alone. `scripts/prerender.mjs` reads and writes `build/client` by name, so build in a scratch worktree instead.
- A build runs with the same values as the `env.js` it is served with, so a push worktree needs the `.env`. Why: a pre-rendered page carries env-dependent markup, the Feedback slot and the chart's product, and React does not patch markup that differs on hydration; it throws the page away (React #418). Production emits `env.js` from the build's own values and CI sets the same values for the build and its stage; `hydration.e2e` loads every pre-rendered page and fails on a drift.

## The site's look

Each rule gives its reason, and a source where one exists outside this repo. A rule whose reason no longer holds is a question for Ryan, not a rule to drop.

- The site teaches by example. The frame is neutral and plain; the exhibits are polished. The home page is Ryan's philosophy of writing frontend code; the demos grow in complexity, accordions first. Why: a reader comes for the exhibits, and a plain frame keeps their eye there. The order lets each demo lean on the one before.
- A tutorial is written for a working developer who has hit the bug its tab is about, often a seasoned one from other work (back end, native, data) who hasn't learned how CSS and the browser work underneath, with newcomers kept in mind. Every term is defined where it first appears, basics included. Headings and captions carry the answer. Every idea has an example to press, and a drawing where it helps. A tab opens with the problem and its point of view, never with how to build. Accordions start with HTML alone, and on the simple tabs depth sits in a fold below the point. Why: a reader who lands from a search with a bug in hand needs the answer before the build, and the less a learner has to attend to, the more room they have to understand. The review holds tutorials to this through `scripts/review/tutorials.md`.
- A code sample's label names what its lines are. "HTML" goes over a sample whose every line is markup, JSX a component returns included. An expression in an attribute or as a child is markup. "TS" goes over any sample with a statement in it: a declaration, a hook, a handler's body, a whole component or file. Why: 34 JSX samples already read "HTML" beside "TS" over logic, and five mixed samples were split between the two (2026-11-07).
- Every literal path given to `repository.file` or `repository.directory` exists in the tree, and `scripts/__tests__/repository-links.spec.mjs` fails on one that doesn't. Why: a move in 5be6c2c2 left the Practice tab's "Four specs" link pointing at a folder that was gone (2026-11-07).
- Anything the frame owns (rail, header, footer, dialogs, controls) is dressed from the frame's own words: `backdrop` ground, `field` bars parted by the `--base` gap, `bare card` inputs under a bold `field` label bar, `path attentive field reachable` for a bar with a word, `icon-button borderless field attentive reachable` for an icon, `hairline-outline` for a secondary, `alarm-ink` for a refusal. The gap is the only empty space a reader sees; parts fill their cells edge to edge. The frame never wears `card`, `rounded-corners`, `lifted`, bordered inputs or filled buttons; those belong to the exhibits. Why: when the frame borrows an exhibit's dress, a reader can no longer tell the site from what it shows. One vocabulary means a new control is dressed by naming its needs, not by writing new rules.
- A primary button is the site's inverted bar, `--field-inverse` with the `--field` word, and every state is drawn: approach on hover and focus, the `--ring` on focus-visible, `--press-glow` on active, `--smoke` or `--ink-muted` when disabled, with no hover. Why: a state that isn't drawn is a state the reader can't see. Keyboard users need to see focus ([WCAG 2.4.7, focus visible](https://www.w3.org/WAI/WCAG21/Understanding/focus-visible.html)), and a disabled button that still lights on hover invites a press that does nothing.
- Markup is form and HTML5 elements only: `dialog`, `form`, `fieldset` with an off-screen `legend`, `label`, `textarea`, `input`, `output`, `button`, `hgroup`, `section` with a heading. A `footer` inside a dialog is a second landmark; an unnamed `section` owes a heading; a group of controls is a `fieldset`. Why: the element is the meaning a screen reader announces, and a `div` means nothing ([HTML, the div element](https://html.spec.whatwg.org/multipage/grouping-content.html#the-div-element)). A native element brings its role, states and keys with it, so ARIA comes last ([the first rule of ARIA](https://www.w3.org/TR/using-aria/)). A group of controls needs its legend to be named ([WCAG technique H71](https://www.w3.org/WAI/WCAG21/Techniques/html/H71)).
- Prose reaches across the container it sits in. No width cap, a measure or any other, stops a paragraph partway across its part of the page. Where words sit beside code or a drawing, that column is their container and they fill it. Why: Ryan, 2026-10-04, "I do not want the text to just suddenly stop in a random part of the page", after the tab introductions were capped at 75 characters and sat beside an empty half of the page. He had said the same on 2026-09-26. A cap for line length leaves a hole that reads as unfinished, and the site's lines are his to set.
- Forms keep their niceties: Enter submits, Shift+Enter makes a new line in a textarea, an empty field is refused in the platform's own words, the phone keyboard's key reads "send", and the contact field offers the reader's email. Why: these are what a reader's hands already expect from every other form. The platform's refusal is worded and translated by the browser and read by assistive tech. The keyboard's key comes from [enterkeyhint](https://developer.mozilla.org/en-US/docs/Web/HTML/Global_attributes/enterkeyhint). Errors follow the established patterns rather than invented ones ([GOV.UK validation](https://design-system.service.gov.uk/patterns/validation/), [Nielsen Norman Group on form errors](https://www.nngroup.com/articles/errors-forms-design-guidelines/)).
- A modal fits the view and never scrolls. On a phone it fills the view, laid out for upright and sideways, and the field is the part that grows. The reset leaves the browser's dialog positioning and backdrop alone and zeroes only its padding and border. Why: a modal that scrolls hides its own buttons, and on a phone the keyboard takes half the view already. The browser's [dialog](https://developer.mozilla.org/en-US/docs/Web/HTML/Element/dialog) already centers itself, dims the page and traps focus, so the reset takes away only what the design replaces.
- Text flows: explanatory prose has no line-length clamp, and each run takes the room its row gives it, as the recipe steps do. Look at the other demos before writing a layout rule. Why: Ryan's ruling, so every demo reads the same way.
- Touch targets are 44px, gated on `pointer: coarse`, never on width. Check both orientations. Why: 44px is the size a finger can hit ([WCAG 2.5.5, target size](https://www.w3.org/WAI/WCAG21/Understanding/target-size.html)). Width says nothing about the pointer: a narrow window on a desktop has a mouse, and a wide tablet has a finger. The [pointer media feature](https://developer.mozilla.org/en-US/docs/Web/CSS/@media/pointer) asks the right question.
- The site's bold is 600 everywhere, through the `bold` modifier in `src/styles/typography.css`, and the frame's sheets declare no font. Why: one weight in one place. A sheet that writes its own weight or size drifts from the rest, and a change to the type scale has to reach every word.
- The platform first: `details` and `popover` before script, and script as the enhancement, so a failure leaves a working page. Why: what the browser does can't break when the script doesn't load, and it comes with keys and announcements already ([details](https://developer.mozilla.org/en-US/docs/Web/HTML/Element/details), [the Popover API](https://developer.mozilla.org/en-US/docs/Web/API/Popover_API), [progressive enhancement](https://developer.mozilla.org/en-US/docs/Glossary/Progressive_Enhancement)). The site is written for browsers that have the features it uses, so a feature every major browser has shipped, such as [invoker commands](https://developer.mozilla.org/en-US/docs/Web/API/Invoker_Commands_API), gets no fallback. Why: Ryan, 2026-11-08, "I am not concerned about older browsers", when the Modal slice dropped the feedback dialog's click fallback because it needed a ref or a lookup by id.
- Every fold moves by transition, never animation. Reduced motion is honored once, in the reset, and then every fold opens at once. Why: a [transition](https://developer.mozilla.org/en-US/docs/Web/CSS/CSS_transitions) turns around from wherever it is when the reader presses again midway; an animation plays out on its own clock. CSS owns all motion, so script only sets state. A reader who asks for [less motion](https://developer.mozilla.org/en-US/docs/Web/CSS/@media/prefers-reduced-motion) gets none, from one block, and no component can forget it ([WCAG 2.3.3, animation from interactions](https://www.w3.org/WAI/WCAG21/Understanding/animation-from-interactions.html)).
- Every gesture has a keyboard twin, in the order the eye reads: one order for the eye and the screen reader. Why: a drag with no keys shuts out anyone without a mouse ([WCAG 2.1.1, keyboard](https://www.w3.org/WAI/WCAG21/Understanding/keyboard.html)), and focus that jumps against the reading order loses the reader ([WCAG 2.4.3, focus order](https://www.w3.org/WAI/WCAG21/Understanding/focus-order.html), [1.3.2, meaningful sequence](https://www.w3.org/WAI/WCAG21/Understanding/meaningful-sequence.html)).
- Diagrams grow to their desktop size and no further, sit centered in a wider column, shrink to a phone's column with their words held at caption size, and draw with non-scaling hairlines. Why: stretched to their column, a label read 27px on an upright iPad and 11px on a phone (#29). Capped at the drawing's own 320px, they read too small on a desktop, so Ryan set the cap at the desktop size. Lines stay hairlines through [vector-effect](https://developer.mozilla.org/en-US/docs/Web/SVG/Attribute/vector-effect).

## Code style

- The reviewers' rubrics below are the style: the three concerns on the home page, `scripts/review/design.md`, `scripts/review/tests.md`, `scripts/review/voice.md` for how the site's prose reads, and `scripts/review/plain.md` for the review's own words.
- A `div` is the very last resort, in any page, exhibit, frame or plain-script build. Each part is the element that says what it is, as the markup bullet above says. A div is never there for layout: a grid on the parent places its own children, and `subgrid` lines up a child's parts with it, so no wrapper is needed to put things side by side or in rows. A div stays only where no element means the part, and the commit that writes it names the elements it ruled out. An existing div that an element or the parent's grid can replace goes when a commit touches its file. Why: Ryan, 2026-11-08, "no divs, I want no divs", then "div should be a last resort, but I really the very last resort" and "we have things like css grid".
- No `document` or `window` in React code, and a ref only for one of two reasons. A component that needs its element uses the platform's declarative attribute for it first: `commandfor` and `command`, `popover`, `autofocus`, a fragment link and `:target`. A `useRef` is allowed only (1) to hold a `dialog` the component shows as a modal with `showModal()`, or (2) to read the element's own details, such as its measured size, when nothing else gives them, such as an event. A behavior that fits neither is dropped. It is never rebuilt with a ref or a lookup by id. `createRef` and `forwardRef` are never used. A value kept between renders is state. ESLint refuses `useRef`, `createRef` and `forwardRef` outside the files listed in `refsWithAReason` in `eslint.config.cjs`. A file joins that list in the commit that adds its ref, and the commit says which of the two reasons it is. Why: Ryan's ruling on refs, relayed by the dev on 2026-10-05; "Platform attributes only" on 2026-11-07, when the ban on `document` met it; and the same day: "there are two expceptions for why a ref is used. one is for a dialog when we need to show a modal. second is if you need the elements details and you have nowhere else to get them from like an event".
- CSS: structure in the component's own sheet, shared needs from `src/styles`, and type only from `src/styles/typography.css` classes on the element. A tag is styled only in the reset; everywhere else a rule names a class, so a table's cells and a fold's parts wear a word. Why: the home page's Presentation concern says "Element selectors are used only in the reset". A rule on a bare tag reaches every such element a later change puts inside the component, and the class list no longer says what the element is. Two gates hold the sheets and the class lists to this: stylelint refuses a look (color, border, type, shadow, radius, fill) in a component sheet, with no excused list, since geometry, counters, opacity and overflow are structure; and ESLint refuses a class no sheet's selector reads and an own class put behind a shared word. An element no sheet styles wears no noun: its tag and its text say what it is, and a class nobody reads says nothing. Why: Ryan, 2026-10-09, "No noun". A component's specific sheet stays near the component and the shared styles at the root. Why: Ryan, 2026-10-09, "in a react app, keep the specific style sheet near the component, and all the shared styles at the root". For the class gate, near means the component's own directory or any directory above it, so a family's shared sheet sits at the family's root, and the shared words in `src/styles` always count. Why: Ryan, 2026-10-09, "Own dir or ancestor", picked from the dev's census (283 classes in 39 files written outside that reach). The table family follows a second ruling of his the same day, "Parts dress themselves": DragSortableTable's parts write their own structural classes and a page passes only its column words; the vanilla table frame is its own world and counts the sheets it imports.
- A comment says why, and only when the cause is outside our control: a browser's behavior, a platform rule, a library's shape, a tool's directive. A comment that says what the code does, or why we chose it, is a sign to refactor or to leave out. Why: Ryan, 2026-10-05, "If code needs a comment to explain what it does, refactor. Comments are for why when the cause is outside our control." The sweep that applied it (about 80 lines in 38 files) kept the comments on WebKit's paint and Tab, Firefox's sixtieths of a pixel, `var()` in `@media`, Coinbase's maker side and the like, and dropped the rest.
- Keep it simple. No performance work without a reader's complaint, apart from holding the Lighthouse byte budgets. Lighthouse's mobile run is a simulated slow phone, not a wait any reader was measured to have, so a gain only it shows weighs less than one a reader meets. A fix that removes machinery beats one that adds it, and a workaround around the framework or the platform goes to the designer before it is built. Why: Ryan, 2026-11-08, "I will wait for a complaint to worry about that, keep it simple. don't use hacks"; and 2026-11-07, of a Lighthouse finding, "but it was synthetcly slow, correct? what slowness are we guarding against?".
- A name never borrows a word HTML, CSS or JavaScript already defines, such as span, window, slice, event, layer, grid, table, content, element, node, document, range, selection or target, unless it means that very thing. Names come from the reader's trade: the Tables column, now `window`, becomes a lookback, a trader's word. A name spells American, as the prose does, so `neighbourOfColumn` becomes `neighborOfColumn`. Existing names take this shape when a commit touches the file that defines them, and that commit renames every use, a tutorial's words included. Why: Ryan, 2026-11-08, "names like it can cognitvely conflict with names that are built into the three concerns", since the site teaches those three.
- No default exports in any file we write: source, scripts, specs and tool configs alike. ESLint's `no-restricted-exports` refuses them in every `.js`, `.mjs`, `.ts` and `.tsx` file, so every module is imported by the name it exports. A tool's config is a `.cjs` file that sets `module.exports`. The defaults left are ones we import but don't write: Vite's `?url` and `?raw` imports and the code the site's own Vite plugins generate. Why: Ryan, 2026-11-07, "NO DEFAULT EXPORTS. this should be a linting rule.", then "no default exports in the config files either" and "module.exports is fine". React Router's framework mode reads a page only from its module's default, so the site left framework mode for data mode, where each route's `lazy` returns the page's named `Room`.
- React code never reaches for `document` or `window`. ESLint's `no-restricted-globals` refuses both in `src`. The plain-script builds are exempt, and they live in their own directories (`vanilla` in `eslint.config.cjs`). If plain-script code sits anywhere else, it moves into its build's directory. The boot files, `src/entry.client.tsx`, `src/hydrateTheSite.tsx` and `src/transport/environment.ts`, are exempt too. The files that still reach for the page are listed in `stillReachForThePage`. A file comes off that list when a commit touches it, and nothing is added. Why: Ryan, 2026-11-07, "react should never need anything to use document" and "if it is in vanlla, then it needs to move to vanilla".
- Motion is the style sheet's alone. Script never starts a transition or an animation: `no-restricted-properties` refuses `startViewTransition` and `animate` in `src`. Script may set a state class or attribute that a style sheet animates, and it may read that an animation ended. Why: Ryan, 2026-11-07, "react should not be in charge of any transitions or animations, nor should javascript" and "they should solely be css's domain".
- Motion moves only what the GPU composites: `transform`, `translate`, `rotate`, `scale`, `opacity` and `filter`. A transition or a keyframe on anything else, `all` included, makes the browser lay out or paint every frame, and stylelint's `chosen/compositor-motion` (scripts/lint/motion.mjs) refuses it. The discrete flips that let an element animate out (`visibility`, `content-visibility`, `display`, `overlay`) are allowed, since they change once and do not move. One layout motion is allowed: a grid track, `grid-template-rows` or `grid-template-columns`, opening from 0fr to 1fr or closing back. A fold's text and a gap in the banner stack open that way, sized by their content with nothing measured. The sheets that still animate other properties are listed in `stillMoveOnTheMainThread` in `stylelint.config.cjs`. A sheet comes off the list when a commit touches it, and nothing is added. The demos have no exception: the Accordions tab's folds and the Charts tab's bars and points move by these properties too, so a lesson about a layout-moving trick shows that trick in its samples, never running. Why: Ryan, 2026-11-07, "motion should also be restricted to the properties that take advantage of the gpu", and "No exceptions" when asked whether the Accordions and Charts exhibits were exempt. The grid track came later the same day: "you could put the row animation on the ::details-content", then "any 0fr↔1fr track".
- A component takes what an element takes: attributes, such as a name, a label or an id, its children, and the handlers an element would fire. State is owned by a context, never passed from component to component. A component that needs state reads it from its context's hook, and a component that changes state dispatches to that context. No prop carries state down or a setter up. State that changes together is one reducer: its parts are one state type, its changes are named actions, and its transitions are one reducer. The context's provider holds it, either through React's `useReducer` or through a store from `@components/store` when middleware has to act after a change, as `DragSortableTable`, Market and Users do. Three or more `useState` calls in a file are a sign of a missing reducer. Values the address holds are read through the context's own hook over the address (`useControls` for the demo dials, `useGallery` for the gallery), never copied into state. Existing files take this shape when a commit touches them. Why: Ryan, 2026-11-07, "if there are many useStates in a file, that is a good chance to use useReducer and maybe a react context", then "I don't think we should ever need to pass state from component to component. I think you geve a component what you would give an element. and state is owned by context".
- A file sits in its context's domain, as `docs/contexts.md` maps them, and some files belong at `src`'s root. A directory holds a subdomain that map names, or one part made of more than one module, such as a component with its style sheet. A single file never gets a directory of its own, and a file never moves only to clear a list entry. `src` has no index, because nothing imports `src` as a module. Why: Ryan, 2026-11-08, "everything needs to be in its domain/context and somethings make sense to be in src", "not everything needs to be in a directory", "if it is in a directory then the directory needs an index" and "get rid of unnecessary directories".
- Every directory of code has an index, and the index is where its exports leave the directory. Code outside a directory imports the directory, never a file inside it. An index exports only what code outside imports, named, from the files directly in it: a subdirectory exports through its own index, and an importer reaches that subdirectory directly. A `.ts` file exports one module, and a `.tsx` file one component, with their types. A module is an object whose name is its namespace, `export const candles: Candles = {mergeLive, bucketTrades};`. It is a function only when it needs something to be built from, or when it holds state of its own, such as a store from `@components/store`, so that each caller and each test gets a fresh one. Its behaviors are always called as methods on that name, `candles.mergeLive(...)`, never destructured or imported loose. Why: Ryan, 2026-11-07, "it onlu needs to be a function if it needs something … else it is just an object and the name serves as a form of namespace" and "then the function is always a method call on the variable". Four ESLint rules in `scripts/lint/structure.mjs` hold this: `one-export`, `has-index`, `through-index` and `index-top-level`. Tests, test support and the framework's route modules are exempt. The files that broke a rule on 2026-11-07 are listed in `scripts/lint/structure-exceptions.json`. A listed file that now keeps its rule fails the lint until it comes off the list, so the lists only shrink, and nothing is added. A commit that moves a listed file moves its entry. Why: Ryan, 2026-11-07, "an index for every directory", "tha is where exports ouside of the directory happen", "but it only exports the top level", "sub-directories export what they export, butt importers need to reach that directory", and "go with the shrinking exception list".
- An index that exports components carries them into every bundle that imports it. So a module that every page loads (the root, the rail, `SideNav`) imports only from indexes that export no components. A value both a component folder and a page-wide module need, such as the concerns, gets a folder of its own. Why: 4d96eb57 sent `practiceAddress` through `@pages/Record/moments` to get `concerns`. Every moment then rode into `hydrateTheSite`, which grew from 66 to 106 KB, and Lighthouse failed on 15 of 16 pages until c570c31e gave `concerns` its own folder (2026-11-08).
- Every list of files that still break a rule ends empty, and the debt pass is not over until it does: `scripts/lint/structure-exceptions.json`, `stillReachForThePage`, `stillMoveOnTheMainThread` and `stillCallComponents`. When a list is empty, the commit that empties it deletes the list and its exemption code. `refsWithAReason` is not debt: it names the two reasons a ref is allowed. Why: Ryan, 2026-11-07, "keep the ratchet, but all must be gone by the end".
- `npm run format` formats with ESLint Stylistic. Lines hold to 120 columns (`max-len`). Strings, template literals, regular expressions and URLs are exempt, so test titles stay whole and searchable. No rule enforces the JSX shape, so it is written here: the first props sit on the tag's line and the rest wrap below it, `>` and the closing tag follow the content, and `return <>` takes no parens. Prose in JSX breaks only between two words in one text run, never beside an element or a `{' '}`, so what renders does not change. Why: Ryan asked for Stylistic in place of WebStorm's reformat on save (2026-11-02). The designer set 120 because it is WebStorm's right margin, the width his saves already kept, and kept the JSX shape the code already had, since he asked for a new tool, not a new look (designer, 2026-11-02).
- Every page is a lazy route whose module exports the page as `Room`, and a reader still gets the whole page in the document. The pre-render loads the matched route before it draws and waits for every part, so no part is written as an empty block for script to fill. The client loads the matched route before it hydrates, so React finds the page it drew. Why: a page written as an empty block was empty to a reader without script, and Lighthouse read its arrival as a layout shift of 0.226 (#243, 2026-10-25). A page whose code had not loaded when React hydrated failed with React error #418 (probe on fbb6105d, 2026-11-07). A frame arriving late moves under the reader's finger ([#126](https://github.com/RyanDur/ChosenPicachu/issues/126), 3fb2e9c0), and the drawn document still prevents that.
- TypeScript is written as modules, never classes. A module is one function that returns an object of behaviors, each one a transformation of data, and a `.ts` file exports that one function and nothing else: no free-floating exported functions beside it, whatever TypeScript's own file modules allow. A React component in a `.tsx` file is its own shape and is not held to this. Those functions are what a result object takes: a step passes them to sand's `Result` or `Maybe`, through `map`, `mBind` or `either`, so the data moves through the result one transformation at a time. sand has three: `Result`, `Maybe` and `asyncResult`. No bare promise appears in `src`: no `await`, no `.then`, no `new Promise`, and no function that returns a `Promise`. A promise the platform hands over, such as a fetch, a service worker's registration or a dynamic import, is wrapped in `asyncResult` where it arrives, and its data moves through `asyncResult`'s functions from there. Tests and journeys may await, since their runners are built on promises. One module serves one domain, in Fowler's sense of a [bounded context](https://martinfowler.com/bliki/BoundedContext.html), and a domain may hold subdomains; `docs/contexts.md` maps the site's contexts and where each file belongs, so a loose function goes inside the module of its context, as one of its behaviors. A module may export its types beside its function. A file whose shape the framework fixes keeps it: `routes.ts` and the promise a route's `lazy` returns, which React Router requires. Page objects are test code, so they may await, and they take the module shape when touched. The [SOLID](https://en.wikipedia.org/wiki/SOLID) principles hold for the modules: each has one reason to change, and a caller depends on the object it is handed, not on how that object was built. Where the platform or a library already does a job, the code uses it, and a hand-written stand-in for it is a hack to remove. Existing files take this shape when a commit touches them, never in a sweep. Why: Ryan, 2026-11-07: "I don't like classes but I do like functions that return objects that transform data that cna be passed into a result object", then "the moules functions can be passed to a reult objects funtions to transform the data", and "we have result maybe and asyncReslt. I shouldn't see any bare promises", and of `src/components/scroll.ts`, "I want to get rid of hacks like this", and "I do not want free floating functions. I know that ts exports as a module. I want one function that retunrs an object of behaviors".
- A module's members never repeat its name or a word the name already says: `travel.eager`, not `travel.eagerTravel`; `tableSelectors.order`, not `tableSelectors.selectOrder`. A module whose name would clash with a value already in use takes another name, as `arrangements` and `lifting` do. Why: the namespace is read at every call, so a repeat is read twice (2026-11-07, the Tables debt slice).
- A name says what the thing is or does, and a value's name says what its values mean, so no one reads the body or the type to learn it. No generic names (`style`, `data`, `value`, `handle`), no abbreviations, and no word dropped from a member when what is left stops naming it: `marks.style` names neither whose style nor what for. Every slice renames what it touches. Why: Ryan, 2026-11-08, "names are importnat", quoting `const style = (toward?: Toward): {'--toward': string} | undefined`, and linking Carl Alexander's [The importance of naming in programming](https://carlalexander.ca/importance-naming-programming/). The design reviewer's rubric holds the detail.
- Presence is said with `has`, `empty`, `is`, `not` or `maybe` from `@ryandur/sand`, never by comparing to `null` or `undefined`. Code that cannot import sand, inside `page.evaluate` or an init script, uses truthiness, `?.` and `??`. ESLint's `no-restricted-syntax` refuses the comparison everywhere. Why: Ryan, 2026-11-07, "we have not is has and empty, why do we ever do this?" The same four replace the symbols: `not(x)` for `!x`, `is(x)` for `!!x`, `empty(list)` for `list.length === 0`, and `has(list)` for a length above zero. Why: Ryan, 2026-11-08, "these four small function make code a lot more readable. symbolic logic is great but does not lend itself to readability unless you are already initiated". Two traps: `empty` and `has` look inside, so a list of DOM nodes, animations or empty items reads as empty, and such a list says `not(list.length)` or `is(list.length)`; and `not` narrows no type, so a guard that narrows says it positively (`if (row) return row;`) or with `maybe`.

## Commits and pushes

- The dev writes and tests code. The designer may change documents and CI without a dev, through its own pull request: this file, the review's rubrics and prompts in `scripts/review/*.md`, and the workflows. Why: Ryan, 2026-10-03, "the dev is in charge of writing and testing code, you can update documents and ci".
- Only reader value becomes a story on the board; tooling is done directly. The designer drafts cards, and a card is promoted when agreed. A Done card is never reopened: a change of direction is a new card. Why: the board is the product's backlog, and the designer verifies each card against what a reader meets. Tooling has no reader to verify for. A reopened card rewrites what was already shipped and checked.
- The dev works on local main so Ryan can watch, uses a worktree only to push a slice ahead, and says "ready" with a clean tree. The designer verifies on main, from the checkout's `build/client`, and holds it until the verdict. Nobody runs journeys while a push is in flight. Why: Ryan sees work only once it's on local main. A verifier who builds from a tree with someone else's uncommitted work measures something that will never be pushed. The journeys share one stage port, so two runs at once test each other's build.
- Before the ready, the dev pushes the card's commits to a branch named `verify/<issue>` (`verify/debt-<area>` for a debt slice, which has no card) rather than running the journeys locally, so neither dev waits for the machine or for the other's run. The dev commits the card on a local branch of the same name. The pre-push hook runs only the linters, which take seconds, so a formatting slip never costs a CI run. The dev opens a pull request from the branch into main (`gh pr create --base main --fill`), and Claude Code reviews it (below). Every check runs on the pull request (`checks.yml`): the linters, the unit tests, the build, the journeys and Lighthouse, then the review. A pull request of documents alone gets only the review, since no page imports a document. Main is never built. When a merge lands, `deploy.yml` finds the pull request, checks that its head holds the same tree as the merged commit, and deploys the site that the pull request's passing checks built, then runs the smoke against it. Why: Ryan, 2026-11-08, "build_test review lighthose and journeys happen on PR's, rebase onto main takes the built artifact from a passing PR and then deploys it to pages and then smoke tests. no pushes to main". The ready names the pull request and its head. After Accepted, the dev queues the merge with `gh pr merge --rebase --auto` and goes on with the next slice, watching the pull request; GitHub merges it by rebase once the checks pass, and deletes the branch. Why: Ryan, 2026-11-08, "the dev can always monitor the pr, and continue going". A fix the pull request needs, a red check or a review finding, is made on its branch: the dev switches to it, commits, pushes, and switches back to main to carry on. Why: Ryan, 2026-11-08, "the dev can always go back to that branch for any fixes then back to main to continue". GitHub holds the merge until the branch is up to date with main, `ready` has passed, and every review conversation on the pull request is resolved (the ruleset "Checks before a merge"). `ready` passes only when every job in `checks.yml`, the review included, passed or had nothing to check. Discuss resolves a conversation when its reviewer answers "Agreed."; the designer resolves one whose fix has landed on the branch, after reading the fix, or on Ryan's ruling. A dev never resolves one. Why: Ryan, 2026-11-08, "doesn't allow merging until all conversations are resolved", and "the feedback is only resolved if it really resolved or discussed". Being up to date is what makes the pull request's site the merged commit's site, so a dev rebases onto main whenever main moves, and the checks run again. No one bypasses the ruleset, admins included. Why: Ryan, 2026-11-08, "require the checks before merging", once main stopped running the checks a pull request had run. A rebase merge writes new commits, so Accepted names the pull request's head, and the dev rebases onto main first if main has moved, by the same rule as before. Why: Ryan, 2026-11-08, "the devs are using branches and those branches can be merged into main via rebase, then they would have code reviews", and "so the branches become PR's".
- A push carries at least seven commits. After the seventh, the dev keeps working until the context in hand is finished, and pushes there, never in the middle of one. A fix for a red check on main is the exception to this and to the next bullet: it goes alone, ahead of any batch, as its own pull request from `verify/main-<what it fixes>`, however small, because every other pull request carries the same red check until the fix is on main. Why: Ryan, 2026-11-07, a red job on main comes first; since 2026-11-08 a merge waits for every check, so the fix can't wait for a batch. This holds for the designer's docs too. Why: Ryan, 2026-11-07, "I want at least seven commits or nearest context grouping after that".
- One push carries a whole slice: its code, its words, and its answers to the last review. Every violation and concern is answered on the pull request that raised it, because its conversation holds the merge: by a fix committed on the branch, or by a reply in its thread that argues against it. A note appears only in the review's summary, holds no merge, and is taken or left on the dev's judgment. One review's answers go in one push. A words-only or one-line fix never gets its own branch: it rides in the nearest push. No one waits for CI: on the designer's Accepted the dev queues the merge and starts the next slice at once. A red check or an open finding holds the merge, so it is answered on the pull request's branch, as above. A red job on main stops the deploy for both devs, so its fix comes first in that push. Why: Ryan, 2026-11-07, "I think we can group more of the debt, we are running ci on text changes, when we have so much to get through", and "that would also mean that we don't have to wait for ci, we can just keep moving, and put any fixes into the next push with the new code". Why: Ryan, 2026-11-07, "we wouldn't always need to wait for the resources to be available if you could push to a branch to run the tests", and that it "can also get feedback"; "main is the big one", and "this way, neither dev needs to wait for the other to be finished", and "we don't need the precommit hook on pushes to branches".
- One commit per fix. A card's batch goes out in one push, after the designer accepts it. Review findings, violations included, are answered in one batch per card. Why: every push costs a full pipeline and a review, and a batch lets the review read the answers together.
- A card is Done when it is in production, every pipeline job is green including the review, and every review finding is fixed, or argued in its thread until the reviewer agrees. Why: the reviewer reads the git log and the thread, not the board.
- A commit quotes the review finding it answers. A decline gives its reason in the finding's thread, where Discuss reads it, and the commit that holds the code as it is says so too: the reviewer reads the log as well as the thread.
- The accordions tab's measured fold, `MeasuredPanel` and the plain fold's script (`Accordions/Plain`), are exhibits of the old way, set beside the platform's way that needs no script. They stay, and a debt pass does not remove them. Why: Ryan, 2026-11-07, "keep the exhibit, it shows the old way".
- A reducer's actions are made by action creators: `dispatch(answered(answer))`, never `dispatch({type: 'answered', answer})`. The creators live beside the reducer, as Feedback's and UserInformation's do. ESLint refuses an object written inside `dispatch(...)`. Why: Ryan, 2026-11-07, "if we are doing a redux style we can create an action creator".
- A component that takes children types them with `PropsWithChildren<Props>`, never with `children` as a key of its props type. ESLint refuses a `children` key in any type. Why: Ryan, 2026-11-07, "we should never have to put children in a props list", "use PropsWithChildren".
- A function that returns JSX is a component, a spec's helpers included. It is named in PascalCase, typed `FC` (`FC<Props>` when it takes props), and rendered as JSX, `<TabHeader topic={topic}/>`, never called as `tabHeader(topic)` or handed to `.map` by name. ESLint's `components/rendered-as-jsx` (scripts/lint/components.mjs) refuses the call, except in the files `stillCallComponents` lists. Why: Ryan, 2026-11-08, "make sure they are using jsx/tsx". React sees a called function as part of its caller, so the function gets no element of its own in the tree and any hook in it runs as the caller's hook.
- A change that shortens a line rejoins the wrap it no longer needs. ESLint's `wrap/needless-wrap` (scripts/lint/wrap.mjs) refuses a value left on its own line after `=` when it would fit on the line above within 120 characters, and `eslint --fix` joins it. Why: Ryan, 2026-11-07, on a `useControls()` call left on the line below its name: the devs were not fixing the formatting when they updated code.
- Linear history: no merge commits. A dev may force-push its own `verify/` branch after a rebase, with `--force-with-lease` (Ryan, 2026-11-07: "yes, let them force-push verify branches"); main is never force-pushed. A dev pushes a new `verify/` branch with `-u` (`git push -u origin HEAD:verify/<name>`), so the local branch tracks it: when GitHub deletes the remote on merge, `git gone` removes the local one. Why: Ryan, 2026-11-07, "we should clean up branches, when the code is on main". Code reaches main through a pull request merged by rebase; the repository allows no merge commit and no squash. Nothing is pushed to main directly, documents included: everything goes through a pull request, so the review reads it, and main holds only what passed. GitHub requires linear history on main, for admins too, and allows no force push. Why: Ryan, 2026-11-07, "we must keep a linear hsitory, rebase only".

## The review

Claude Code's own `/code-review` reviews each pull request into main, through `anthropics/claude-code-action` in the review job of `.github/workflows/checks.yml`, once the build and the unit tests pass, and holds it to the rubrics under Reviewers below as well as to correctness. It leaves its violations and concerns on the pull request's lines and lists every finding, notes included, in its summary comment. Every finding carries a severity (violation, concern or note) and the rubric it answers to, and a violation turns the job red. `scripts/review/ask.mjs` builds the request from the list under Reviewers, so a reviewer added there joins the next review, and one removed there leaves it. The review answers in the shape `scripts/review/findings.schema.json` sets, and `scripts/review/report.mjs` turns that answer into the comment and the verdict. Why: Ryan, 2026-11-08, "can we switch to the claude code reviewer for the branches? it cna use our reviewing standards".

Whoever disagrees with a finding, or has fixed it, replies in its thread with the reason or the commit, and `.github/workflows/discuss.yml` has the reviewer answer there: "Agreed." when the fix or the argument holds, "Not yet." with what still needs doing when it doesn't. Discuss resolves the thread on "Agreed." and reruns the head's review job once the run ends, so the review reads the agreement and `ready` can turn green. A designer rules with a reply in the thread that ends "Resolved by ruling.", resolves the thread, and reruns the review job by hand (`gh run rerun --job <review job id>`), which runs `ready` again; a failed journey or Lighthouse job is never rerun, since one that passes only on retry is a defect. Discuss does not answer a ruling. A thread answered "Not yet." stays open until the two agree, or until the designer rules and resolves it. A ruling is final: a later "Not yet." on a resolved thread is a record, and does not reopen it. A reply on a merged pull request is answered by running Discuss by hand with the pull request and the reply's id. Copilot's review comments are answered the same way, by reply, and resolved when the reply holds. Why: Ryan, 2026-11-08, "close the addressed reviews and reply to the ones you don't agree with and have a discussion on what needs to be done or they agree", and of Copilot's review, "might as well take its feedback into consideration as well".

### Run it before a push

From the repo's root, on the commits about to be pushed:

```sh
export REVIEW_BEFORE=$(git rev-parse origin/main) REVIEW_AFTER=$(git rev-parse HEAD)
claude --print "$(node scripts/review/ask.mjs)" --output-format json \
  --json-schema "$(node -e "process.stdout.write(JSON.stringify(require('./scripts/review/findings.schema.json')))")" \
  --allowedTools "Agent,Read,Grep,Glob,Skill,Bash(git diff:*),Bash(git log:*),Bash(git show:*)" \
  --max-turns 80 --no-session-persistence > review.json
node scripts/review/report.mjs < review.json
```

The pipeline runs the same through `npx --yes @anthropic-ai/claude-code@2.1.319` with its own model.

The request asks for every finding with `--max-findings all`. The code-review skill keeps that choice for later reviews in your own Claude Code until you pass `--max-findings default`.

## Reviewers

Each rubric is read whole before the review, and a finding is reported against it only where its rule holds.

### structure
- rubric: `src/pages/Practice/structure/StructurePractice.tsx`
- asks: what things are: the element chosen for the content, the landmarks and their names, the headings, the reading order with the styles off

### presentation
- rubric: `src/pages/Practice/presentation/PresentationPractice.tsx`
- asks: how things show: structure in the component sheet, needs as shared words, the platform's own states before invented ones, constants in the sheet and only runtime values inline

### dynamic-interaction
- rubric: `src/pages/Practice/behavior/BehaviorPractice.tsx`
- asks: how things respond: state that holds only what cannot be derived, events named for what happened, pure transitions, the platform's behavior before script, a keyboard twin for every gesture, changes that announce themselves

### design
- rubric: `scripts/review/design.md`
- asks: how the code is shaped so that change stays cheap: where a thing lives on the app continuum, what the types allow and forbid, and how failure travels on the two tracks of a Result; names that say what a thing is and what its values mean; a functional core under an imperative shell

### tests
- rubric: `scripts/review/tests.md`
- asks: what a test is for: readable, worth having, pinning behavior and not implementation, at the right level, against the real thing, and whether a test is missing; Beck's properties for unit tests, Dodds' practice for component specs, Fowler's journeys and Playwright's practices for e2e, Fowler's page objects beside their owner

### tutorials
- rubric: `scripts/review/tutorials.md`
- asks: what a tutorial on the demos tab owes its reader: claims that are true, a sentence after the opening saying what the tab assumes from earlier tabs with a link to each, terms defined where they first appear, each shared term taught in full on one tab and glossed and linked on the rest, and mechanisms explained before the first build that uses them, a method the cards are told in walked through once before the first card, headings that lead with the answer, an example to press for every idea, a tab that opens with why, the smallest script first with the site's build behind it, the mechanism said in plain words, one idea in each run, a point stated and not staged

### record
- rubric: `scripts/review/record.md`
- asks: what the record owes its reader: moments that agree with each other on every date, name, count and claim, quotations that are the source's words with a signpost to their page and the page on the shelf, prose that says what each quotation shows, and history told from the sources in the third person

### voice
- rubric: `scripts/review/voice.md`
- asks: how the prose reads, in the author's voice after Fowler and Beck: one point per paragraph opening on something doing something, the fact stated before it is built on, the thing then its reason with no claim wider than the evidence, no blame and no performance, trades told as trades and preferences in the first person, the depth where it belongs, and flow heard aloud
