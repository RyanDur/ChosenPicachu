# The tutorials door

The home page states what the site is, how it shows, and how it responds. The tests door states what a test is for, and the design door how the code is shaped. This door states what a tutorial on the demos tab owes its reader. You hold every exhibit, run, caption, heading and recipe step on the demos tab to this door: the words a reader reads and the examples a reader presses. You hold nothing outside it.

## The reader

A tutorial is written for a working developer who has hit the bug the tab is about, often arriving from a search with it in hand. Many are seasoned developers from other work, such as the back end, native apps or data, who have not learned how CSS and the browser work underneath. A newcomer reads the same page and is kept in mind. Read every word as this reader would, and ask whether they could follow it.

## The order of the tabs

The tabs run from simple to expert. Accordions come first, and the page begins with HTML alone, because the less a learner has to attend to, the more room they have to understand. Z-index is the next step. Drag sort, charts and tables are the deep end. A change that makes a simple tab harder to start, or puts expert depth in plain view on it, breaks this order. On a simple tab the depth belongs in a fold below the point.

## Seven questions, in order

1. **Is it true?** Every claim a run makes about CSS, HTML, the browser or the code holds, in every engine the site supports. A claim the platform or the code contradicts is a violation. Trace it to what the reader would believe and go on to get wrong. A run that teaches the mistake its tab exists to fix is the worst case.
2. **Is every term defined where it first appears?** A term the tab has not defined, used before its definition or never defined, is a finding. Name the term and the line. Basics count when a run leans on them: selector, positioned, event, attribute, viewport. A name from a framework (hook, effect, reducer, store) is defined by what it does here, in plain words. "MDN" is named once per tab as Mozilla's web reference.
3. **Does the answer lead?** A heading or caption says what happens, so a reader who reads only those learns the point. A heading that is a slogan, a figure of speech or a coined word ("a third's stray", "aloft", "the road") is a finding. The run beneath can explain at length; the heading cannot hide the answer.
4. **Does every idea have an example to press?** An idea told only in prose, with nothing on the page to try, is a finding when an exhibit could show it. A rule about geometry or order, such as where a drag crosses or what paints over what, also wants a drawing in the site's drawing vocabulary.
5. **Does the tab open with why?** A tab opens with the problem it is about and its point of view, then leads into its first example. It never opens with how to build the feature. Building comes later, in its tutorial.
6. **Does it say the mechanism?** A run says what the code or the browser does, not how it feels. "The origin whispers in its seat" becomes the property the code sets and its value. An implementer's detail, such as a browser quirk or why an attribute is there, stays, but in plain words and after the idea it serves.
7. **Is each run one idea?** A run that chains several new ideas in one paragraph, so the reader must hold them all at once, is split. A sentence said in two places on the tab is a finding against the second.
